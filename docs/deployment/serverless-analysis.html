Serverless Strategy Analysis

Honest opinion on whether serverless is the right model for this app, plus a detailed AWS CDK vs Vercel + QStash comparison with cost estimates and migration effort.

Verdict: Is Serverless Right?

Short answer: yes. This app was designed for serverless from day one.
✅
Serverless is the right choice
Image generation jobs arrive in bursts, not steady streams. The worker is already event-driven via SQS. AI API calls are the bottleneck — Lambda sits waiting, and Lambda is orders of magnitude cheaper per-idle-second than a container.
Excellent fit
⚡
Two viable platform choices
AWS CDK (current plan) wins on cost at scale. Vercel + QStash wins on ops simplicity and faster iteration velocity. Both are genuinely viable — the right choice depends on team priorities.
Decision required
🐘
PostgreSQL: use Neon
The only non-serverless piece is PostgreSQL. Neon is recommended — serverless Postgres with pgvector support, scales to zero, and is not AWS-locked. Avoids RDS always-on pricing at low scale.
Neon recommended

Why This App Fits Serverless

Six design signals that confirm serverless was the right architectural choice
📈
Bursty, not constant load
Image generation jobs arrive in batches. An always-on server would be idle most of the time. With Lambda, you pay for compute only when jobs run.
Strong fit signal
📬
SQS decoupling already exists
The worker is already event-driven. Serverless is the natural runtime for an event-driven consumer. The SQS → Lambda wiring is almost zero configuration.
Designed for serverless
⏳
AI API calls are the bottleneck
Lambda sits waiting for OpenAI/Replicate to respond. You pay for wall-clock time whether on Lambda or a container — but Lambda is far cheaper per idle second.
Cost optimal
🌐
OpenNext already wired
open-next.config.ts configures aws-lambda-streaming mode. The web app build pipeline is Lambda-ready out of the box.
Zero web migration needed
🖥️
@sparticuz/chromium included
The renderer uses @sparticuz/chromium — a deliberate dependency on the Lambda-optimized Chromium binary. This was a design choice that signals serverless intent.
Built for Lambda
🔌
Storage and queue abstracted
SqsQueueAdapter, StorageAdapter, and their MinIO/ElasticMQ local equivalents mean core business logic has no direct cloud-SDK dependency.
Provider-agnostic core

Cost Comparison

Estimates for a small production app: ~10,000 image jobs/month, ~50,000 web requests/day
☁️ Option A — AWS CDK
Lambda Web (50k req/day × 30 days × 0.5s avg × 1024MB) $4–8
Lambda Worker (10k jobs × 30s avg × 1536MB) $6–12
SQS (10k messages + polling) ~$0.01
S3 (10k images ~1MB each = 10GB + transfers) $2–5
CloudFront (50k req/day, ~5GB transfer) $3–6
SSM Parameter Store (standard) Free
Total estimate $15–31/mo
▲ Option B — Vercel + QStash
Vercel Pro (web + worker functions) $20 flat
Vercel compute beyond included quota $0–5
QStash / Upstash (10k msg/mo — within free tier) $0
S3 or Vercel Blob (10k images ~10GB) $2–5
   
   
Total estimate $22–30/mo
Scale notes: At small scale (10k jobs/month), both options cost roughly the same — Vercel Pro's flat fee dominates. At medium scale (100k jobs/month), AWS Lambda pulls ahead on per-execution pricing. At high scale (1M+ jobs/month), AWS is significantly cheaper. Vercel's advantage is developer velocity, not compute cost. Neither estimate includes DB (Neon free tier for early stage; ~$19/month after) or AI API costs (which dominate at any real scale).

Option B Migration Effort (AWS → Vercel)

~4–6 days of work. All business logic is untouched — only infrastructure edges change.
1–2 hrs

Switch OpenNext adapter

Change open-next.config.ts from aws-lambda-streaming to the Vercel adapter. No Next.js app code changes required.

1 day

Create Vercel worker HTTP handler

Write apps/worker/src/vercel-handler.ts — wraps the existing GenerationWorker and CaptionWorker as an HTTP POST route that QStash can call. The worker logic itself doesn't change.

1–2 days

Write QStashQueueAdapter

Implement the existing QueueAdapter interface using QStash's HTTP-push API. The abstraction already exists — this is a new adapter, not a rewrite. Replace SqsQueueAdapter with QStashQueueAdapter in the Vercel config.

0.5 day

Replace queue bootstrapping

Replace the queue:bootstrap script (ElasticMQ setup) with QStash topic configuration. QStash config is minimal — one topic per queue.

1 day

Move secrets to Vercel environment variables

Replace SSM GetParameter calls with process.env reads populated by the Vercel dashboard. Remove the SSM client dependency from both Lambdas.

0.5 day

Remove CDK stacks (optional)

Delete infra/lib/web-stack.ts and infra/lib/worker-stack.ts. Keep the storage stack if continuing to use S3, or replace with Vercel Blob.

Decision Summary

When to choose each option
☁️
Option A — AWS CDK
Deploy the 4 CDK stacks as written. Add Neon for PostgreSQL. Populate SSM parameters before first deploy.
Choose this if:
  • • Cost efficiency at scale matters more than ops simplicity
  • • You want full control over IAM and infrastructure
  • • You expect to scale to 100k+ jobs/month
  • • Team has AWS experience
▲
Option B — Vercel + QStash
Switch OpenNext adapter, add QStash worker handler, replace SSM with env vars. ~4–6 days migration.
Choose this if:
  • • Fastest path to production with least ops overhead
  • • Still in rapid iteration phase — preview URLs per PR matter
  • • Small team, no dedicated DevOps
  • • You want one-click rollbacks and zero CI/CD setup
Migration note: Because queue, storage, and AI gateway are abstracted, you can switch from Option B back to Option A at any time: swap in SqsQueueAdapter for QStashAdapter, switch open-next.config.ts back to aws-lambda-streaming, re-deploy CDK stacks. The business logic never changes — migration is at the infrastructure edges only.
