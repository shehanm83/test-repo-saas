SQS Queue Configuration & Timeout Math

Why visibility timeout (180s) is larger than Lambda timeout (120s) — the 60-second safety buffer
Queue Name Visibility Timeout Max Receive Count DLQ After
Generations layertone-{stage}-generations 180s 3 3 failed attempts → DLQ
Captions layertone-{stage}-captions 60s 3 3 failed attempts → DLQ
DLQ layertone-{stage}-generations-dlq N/A N/A 14-day retention
Timeout math for Generations queue:
Lambda timeout
120s
Maximum time the worker can run before Lambda kills the invocation
SQS visibility
180s
Message hidden for 180s after being received — other consumers can't see it
Safety buffer
60s
If Lambda times out at 120s, SQS waits 60 more seconds before re-delivering the message
The 60s buffer prevents an immediate re-delivery after timeout. Without it, a timed-out job would be re-queued instantly and could spin into DLQ in seconds. The idempotency check at the start of the worker handles the case where a job is re-delivered after a timeout.

S3 Object Key Structure

Canonical key patterns used by @layertone/storage via the keys module
workspaces/{workspaceId}/brands/{brandId}/assets/{assetId}/{filename}
Brand assets (logos, reference images, color swatches). Used for brand grounding via pgvector embedding similarity.
workspaces/{workspaceId}/gen/{generationId}/variant/{variantId}/background.png
Raw AI-generated background image — before template overlay rendering. Preserved for re-rendering with different templates.
workspaces/{workspaceId}/gen/{generationId}/variant/{variantId}/output.png
Final rendered output — background + brand overlay + text slots. This is the URL presigned and delivered to the user.
workspaces/{workspaceId}/inspiration/{uploadId}/{filename}
User-uploaded inspiration images. Tagged ttl:24h → automatically deleted by S3 lifecycle rule after 1 day.
global/templates/{templateId}/preview.png
Template preview images stored in the Global Assets bucket. Long-lived — no lifecycle expiry.
global/stock/{stockId}/{filename}
Stock images available to all workspaces. Stored in Global Assets bucket.

S3 Lifecycle Rules (App Assets Bucket)

Automatic cleanup rules on layertone-app-{stage}-assets to control storage costs
Rule ID Prefix Condition Action
expire-noncurrent workspaces/ Object is a noncurrent version (overwritten or deleted) Delete after 30 days — reclaims space from old generation images
abort-mpu workspaces/ Incomplete multipart upload Abort after 1 day — prevents abandoned uploads from accumulating
expire-inspiration-stage workspaces/ Object has tag ttl=24h Delete after 1 day — inspiration uploads are temporary, not stored long-term

CI/CD Deploy Pipeline

Automated pipeline in .github/workflows/deploy.yaml — staging gates production
staging

Staging Deploy — triggered on push to main or manual dispatch

Uses GitHub OIDC role assumption (AWS_DEPLOY_ROLE_STAGING) — no long-lived AWS keys stored in GitHub secrets.

Checkout → pnpm install (frozen lockfile)
DB Migrate → pnpm --filter @layertone/db db:migrate using STAGING_DATABASE_URL
Build Web → pnpm --filter @layertone/web build:lambda — runs OpenNext build, outputs to .open-next/
Build Worker → pnpm --filter @layertone/worker build — TypeScript compile to apps/worker/dist/
AWS Auth → aws-actions/configure-aws-credentials@v4 with OIDC role assumption, us-east-1
CDK Deploy → cdk deploy --all --require-approval never --context env=staging
production

Production Deploy — runs after staging succeeds (needs: deploy-staging)

Identical steps to staging but uses AWS_DEPLOY_ROLE_PROD and --context env=prod. Requires manual approval if the GitHub environment is configured with a protection rule.

Same build steps as staging (fresh checkout, install, migrate, build)
AWS Auth → OIDC role AWS_DEPLOY_ROLE_PROD
CDK Deploy → cdk deploy --all --require-approval never --context env=prod
